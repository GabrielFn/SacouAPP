# E2.3 · Saque, side-out e rotação por time (`setterZone`)

**As 3 perguntas foram respondidas pelo Gabriel em 02/11/2026 (`perguntas.md`): 1, 2 e 1, as recomendações abaixo.** O evento grava o resultado em todas. Detalhes na seção 8.

1. Em que rotação cada time começa o set seguinte. **Recomendação: continua de onde parou.**
2. Quem saca primeiro no set decisivo. **Recomendação: sorteio no set decisivo de md3 e md5.**
3. Time que não tem 6 jogadores (areia 2x2 e 4x4, pelada com 5). **Recomendação: rotação desligada, e o app mostra só o time que saca.**

**Sensível para segurança: sim.** O `MatchStarted` ganha um campo novo com `MemberId` (`rotations.*.lineup`) e há campos novos em dois parsers de entrada não confiável. Passa pelo `revisor-seguranca`, com escopo proporcional: parser fechado, `lineup` contido no time, erro sem valor recebido e custo do log hostil. Não há tipo de evento novo.

**Dependências:** E2.2 e E1.1 (feitas). **Desenvolvedor:** Opus (regra do motor). **Branch:** `task/E2.3-serve-rotation`.

## 1. Objetivo e critério de aceite

Backlog (`plano-mvp.md:119`): "Saque, side-out e rotação por time (`setterZone`)". **Aceite:** "Nunca gira quem venceu sacando; sequência 1→6→5…4→3→2".

Na prática: o motor sabe qual time saca, quem é o sacador e a rotação de cada time, a cada ponto, no desfazer e na virada de set.

| Parte do aceite | Onde é demonstrada |
|---|---|
| Nunca gira quem venceu sacando | Casos `s1-*`, `s6-*`, `s13-*` e o teste exaustivo da seção 6.4 |
| Sequência 1→6→5→4→3→2 | Casos `s3-step-01` a `s3-step-12` e `zone-*-next-*` |

### Por que o side-out é derivado (D1)

`decisoes.md:26` e o ADR 0009 pedem que o evento grave o resultado das regras. Esta é uma **exceção consciente e estreita**, a registrar no ADR 0024 e a citar no relatório do M2. O objetivo daquela regra é não manter dois motores (`revisao-mvp.md:121`, "sem reimplementar toda a lógica"), e aqui o porte são duas funções de uma linha. O `PointScored` já é a exceção aceita: o aplicador soma 1 (ADR 0023:13).

| Opção | O que acontece com dois escritores intercalados ou evento atrasado (`eventos.md:88, 90`) | Veredito |
|---|---|---|
| Evento próprio `SideOut`, depois do ponto | Dois celulares veem o mesmo rali e os dois emitem: ou gira duas vezes, ou o segundo é rejeitado e trava o stream, o que `eventos.md:90` proíbe. Gravar só um dos dois deixa o saque errado. O desfazer pode cair entre o ponto e o giro, e o log dobra nos ralis com side-out | Recusada |
| `PointScored` com zona gravada, **com** conferência | A intercalação vira `event-rejected` e trava o stream: é o motivo de ADR 0023:13 | Recusada |
| `PointScored` com zona gravada, **sem** conferência | Não trava, mas o resultado é errado: `b` gravado com "sem side-out" depois de `a` ter retomado o saque deixa quem venceu recebendo sem o saque e sem girar. Além disso, um evento forjado escolhe a rotação | Recusada |
| **Derivar do estado** | Cada ponto é julgado no estado da ordem canônica: sem rejeição, determinístico e sempre coerente. Ninguém consegue forjar uma rotação marcando ponto | **Escolhida** |

Vale gravar quando a escolha é de alguém ou o resultado não sai do estado: `firstServer`, `setterZones` do set seguinte e as correções da E2.7.

## 4. Payloads e estado

### Payloads (schema 1)

| Tipo | Payload (a ordem é a da conferência de campos) |
|---|---|
| `MatchStarted` | `{ matchId, rulesVersion, scoring, teams, firstServer, rotations: { a: { lineup, setterZone } \| null, b: { lineup, setterZone } \| null } }` |
| `PointScored` | **Sem mudança:** `{ matchId, setNumber, team }` |
| `SetEnded` | `{ matchId, setNumber, winner, nextSet: { targetPoints, firstServer, setterZones: { a, b } } \| null }` |
| `MatchEnded` | Sem mudança |

- `firstServer` é `a` ou `b`. `setterZone` é inteiro de 1 a 6. `setterZones.a` e `.b` são inteiros de 1 a 6 ou `null`.
- `null` é serializado, nunca omitido: `rotations.a` ausente é `invalid-payload`, e **não** equivale a `null`.
- `lineup` fora das regras de D6, inclusive com membro fora do time, é `invalid-payload` em `rotations.<lado>.lineup`.
- `field`s novos: `firstServer`, `rotations`, `rotations.a`, `rotations.a.lineup`, `rotations.a.setterZone`, os três equivalentes em `b`, `nextSet.firstServer`, `nextSet.setterZones`, `nextSet.setterZones.a` e `nextSet.setterZones.b`.
- Ordem: desconhecido primeiro, em qualquer nível; depois a da tabela, e `rotations` vem depois de `teams` porque confere o `lineup` contra ele. Os casos `MatchStarted-order-*` existentes não mudam.

Exemplo:

```json
{
  "firstServer": "a",
  "matchId": "f0000000-0000-4000-8000-000000000001",
  "rotations": {
    "a": { "lineup": ["<6 MemberId, levantador primeiro>"], "setterZone": 2 },
    "b": null
  },
  "rulesVersion": 1,
  "scoring": { "bestOf": 3, "pointsPerSet": 25, "tieBreakPoints": 15, "winMargin": 2 },
  "teams": { "a": { "memberIds": ["..."] }, "b": { "memberIds": ["..."] } }
}
```

### Estado (chaves na ordem real)

```
TeamState { lineup: MemberId[6], setterZone: 1..6 }   // E2.4 e E2.5 acrescentam campos
MatchSet  { firstServer, score: { a, b }, servingTeam, setNumber, targetPoints }
MatchScore { completedSets, currentSet: MatchSet | null, matchId,
             rotations: { a: TeamState | null, b: TeamState | null },
             rulesVersion, scoring, setsWon, teams }
FinishedMatch { completedSets, currentSet, endReason, matchId, rotations, rulesVersion,
                scoring, setsWon, teams, winner }
```

`completedSets`, `teams` e `CourtSessionState` não mudam. **`teams` segue como a cópia congelada do evento, e `rotations` é a parte que muda.** Por isso o `lineup` fica no estado corrente: a E2.5 e a escalação em jogo (`Escalacao.dc.html`) trocam jogador ali, sem mexer no congelado.

### Aplicadores

| Evento | Efeito novo | `event-rejected` novo |
|---|---|---|
| `MatchStarted` | `currentSet.firstServer` e `servingTeam` recebem `firstServer`; `rotations` é copiado | Só o parser |
| `PointScored` | D2 | Nenhum: não há resultado gravado para conferir |
| `SetEnded` | Set novo com `firstServer` e `servingTeam` gravados; `setterZone` de cada time recebe o valor gravado, com o `lineup` mantido. Com `nextSet: null`, `rotations` fica como está | `setterZones` com zona em time sem rotação, ou `null` em time com rotação. É estrutura, não regra: não olha placar nem alternância |
| `MatchEnded` | Copia `rotations` para a partida terminada | Nenhum |

### Comandos

- `startMatch`: a entrada ganha `firstServer` e `rotations`, validados pelo parser. Sem código novo de recusa.
- `scorePoint`: sem mudança, e o evento continua sem rotação.
- `confirmSetEnd(state, options?: { firstServer?: TeamSide })`: sem `firstServer`, alterna; `setterZones` são as atuais. O valor passa pelo parser, então o que for inválido volta como `invalid-payload` em `nextSet.firstServer`. A pendência de `MatchEnded` não muda.

### Regras puras (`score/rotation-rules.ts`)

| Função | Retorno | Uso |
|---|---|---|
| `nextSetterZone(zone)` | A casa seguinte de `SETTER_ZONE_SEQUENCE` | Aplicador; E2.7 |
| `isSideOut(servingTeam, pointWinner)` | `boolean` | Aplicador; vibração no side-out (`produto.md:138`) |
| `getNextSetFirstServer(firstServer)` | O outro lado | Comando; texto da tela 25 antes de confirmar |
| `getLineupBySlot(lineup, setterZone)` | Array de 6, do slot 1 ao 6, sem chave numérica | Telas 09, 10 e 22 |
| `getServingPlayer(lineup, setterZone)` | `MemberId` do slot 1 | `ServingPlayer`, telas 09, 10 e 24 (`rotacoes.md:64`) |
| `getCurrentServingPlayer(match)` | O mesmo para o time que saca, ou `null` sem set aberto ou sem rotação nesse time | Telas 09 e 10 |

### Custo por evento e limite

| Item | Custo |
|---|---|
| `PointScored` sem side-out | Igual ao da E2.2: `MatchScore`, `currentSet` e `score` rasos, com duas chaves a mais em `currentSet` |
| `PointScored` com side-out | Mais 2 objetos pequenos (`rotations` e o `TeamState` de um time). O `lineup` é compartilhado, sem cópia |
| `SetEnded` | Mais até 3 objetos de tamanho fixo, com os `lineup` compartilhados |
| `MatchStarted` e `FinishedMatch` | Mais 2 `TeamState` com 6 referências cada, por partida |
| Histórico no estado | **Nenhum:** nenhuma lista cresce a cada ponto ou side-out |

Por evento o custo é O(1), e **o tamanho do estado não depende do número de ralis**. Vale o limite existente, `MAX_FINISHED_MATCHES` (200), e nenhum novo é necessário. O `MatchStarted` no maior caso tem menos de 100 valores, longe dos 4096 de `MAX_PAYLOAD_NODES`. Como antes, o replay retém um nó por evento ativo e o tamanho do log é da E3.7. O pior caso agora é side-out em todo ponto: o testador refaz a medição de 64 mil eventos citada em `modelo-de-ameacas.md:47` e atualiza o número.

### 6.3 `score-payloads.json`

**Matriz (já automática pelo teste):** `MatchStarted`, faltando cada campo novo e com nome proibido e chave estranha em `rotations`, `rotations.a` e `rotations.b`. `SetEnded`, o mesmo em `nextSet.setterZones`. O `-valid` de cada tipo tem rotação e `nextSet` preenchidos, para esses níveis existirem.

**Valores (`MatchStarted`):**

- `firstServer` `b`, `"A"`, `"c"`, `null`, `1`.
- `rotations` como array; `rotations.a` e `.b` como `null` (válido, juntos e um de cada vez), como array, número, `{}` e ausente.
- `lineup` com 5, 7 e 0 itens, não array, repetido, UUID maiúsculo, e-mail, nome, UUID com `\n`, número, `null`; membro fora do time; membro do outro time.
- `setterZone` 1 e 6 válidos; 0, 7, 1,5, `"1"`, `null`.
- Ordem: `teams` antes de `firstServer`; `firstServer` antes de `rotations`; `rotations.a` antes de `rotations.b`; `lineup` antes de `setterZone`.
- `rotation`, `lineup` e `setterZone` na raiz são `unknown-field`.

**Valores (`SetEnded`):**

- `nextSet.firstServer` ausente, `null`, `"A"`.
- `nextSet.setterZones` ausente, array, `null`; `a` e `b` em 1, 6 e `null` válidos; 0, 7, 1,5, `"1"` e ausente.
- Ordem: `targetPoints`, `firstServer`, `setterZones`.

**`PointScored`:** `sideOut`, `setterZone` e `servingTeam` são `unknown-field`.

### 6.4 Só em TS

- **Exaustivo:** todas as sequências de 8 ralis (2^8) com cada `firstServer`. Em cada passo, um oráculo independente no teste confere: `servingTeam` é o último vencedor; quem venceu sacando manteve a zona; quem venceu recebendo andou uma casa; o outro time não mudou.
- **Constante:** `SETTER_ZONE_SEQUENCE` igual a `FORMATION_CATALOG.systems["5x1"].rotationOrder`.
- **Comandos, alternância:**
  - `firstServer` a e a vence o set → próximo b.
  - `firstServer` a e **b vence** o set → próximo b (reprova "quem perdeu saca").
  - `firstServer` b e a vence o set → próximo a (reprova "ímpar saca a").
  - md5 inteiro: a, b, a, b, a.
  - Com `options.firstServer`, vale o informado; inválido é `invalid-payload` em `nextSet.firstServer`.
- **Comandos, geral:** `confirmSetEnd` grava as zonas atuais; `scorePoint` emite só os 3 campos; partida inteira por comandos, com parser e replay, dá o mesmo estado que `s13`.
- **`getCurrentServingPlayer`:** `null` sem set aberto e sem rotação no time que saca; segue o sacador depois de cada side-out.
- **Pureza:** aplicadores não mudam estado congelado em profundidade; `Object.prototype` poluído não preenche `rotations.a` ausente; erro não contém o valor recebido (canário em `lineup`); o estado sobrevive a `JSON.parse(JSON.stringify())`.
- **Volume, com `VOLUME_TEST_TIMEOUT_MS` e sem conferir tempo:**
  - 10 mil pontos alternados, com side-out em todos, sem estouro.
  - Tamanho do estado independente dos ralis: `JSON.stringify(state).length` com 1 mil e com 10 mil pontos difere só pelos dígitos do placar.
  - 200 partidas terminadas com 24 membros por time e rotação nos dois, mais a 201ª rejeitada.

## 7. Contrato para a E2.10 (ADR 0024)

**A E2.10 porta parsers e aplicadores, mais as funções de `rotation-rules.ts`: `nextSetterZone`, `isSideOut`, `getNextSetFirstServer`, `getLineupBySlot` e `getServingPlayer`. `getCurrentServingPlayer` serve às telas e fica só em TS. Roda `rotation-rules.json` e `rotation-events.json` pelo caminho, além dos golden do ADR 0023.** Comandos ficam só em TS, salvo decisão da E3.7.

| Arquivo | Formato |
|---|---|
| `rotation-rules.json` | `{ id, rule: "zone" \| "side-out" \| "next-first-server", input, expected }`. `zone`: `input { lineup, setterZone }`, `expected { nextSetterZone, lineupBySlot, servingPlayer }`. `side-out`: `input { servingTeam, pointWinner }`, `expected { isSideOut }`. `next-first-server`: `input { firstServer }`, `expected { firstServer }` |
| `rotation-events.json` | Mesmo formato de `event-log.json` |

Pontos de divergência, além dos dos ADR 0022 e 0023:

- **A transição é a única regra no aplicador:** a tabela de `nextSetterZone` em C# precisa ser a mesma constante, sem aritmética própria. Módulo de número negativo em C# difere de uma implementação ingênua; use índice na tabela.
- **Ordem de chaves:** `rotations` vem antes de `rulesVersion`, e `setsWon` continua antes de `teams`. O golden compara texto.
- **`null` de `rotations.*` e `setterZones.*` é serializado, nunca omitido.** Atenção a `JsonIgnoreCondition`.
- **Ausente diferente de `null`:** o parser C# precisa distinguir, como `readOwn`.
- **`lineup`** preserva a ordem, e sua conferência contra `teams` usa comparação ordinal.
- **Casos só em TS:** comandos, exaustivo, canário, `Object.prototype` poluído, congelamento e volume.

## 9. Riscos

- **Exceção a `decisoes.md:26`:** o revisor pode ler a derivação como desvio. Está justificada na seção 3 e vai para o ADR 0024 e o relatório do M2. `decisoes.md` não muda sem o Gabriel.
- **Regra no aplicador:** é a primeira regra do vôlei no replay. Mudar a transição exige `schemaVersion` novo (D3). Editar a constante em silêncio mudaria partidas gravadas, e o golden `s3-*` é a trava.
- **Evento prova formato, não verdade:** `rotations`, `firstServer` e `nextSet.*` passam no replay mesmo falsos, e mudam quem saca. É a mesma classe de `targetPoints` (ADR 0023). **Para a E3.7:** conferir `rotations` contra a escalação, `nextSet.firstServer` contra a regra ou sorteio autorizado, e `setterZones` contra o estado. Marcar ponto, em si, não dá poder novo sobre a rotação.
- **`setterZone` na Livre:** o nome engana, porque não há levantador. A nota vai no glossário e no ADR 0024; a tela não mostra número nesse sistema (`rotacoes.md:48`), e a E2.4 mapeia para a chave `0`.
- **Rali final gira:** um side-out no ponto que fecha o set gira o time, e a rotação segue para o set seguinte na opção 1 da pergunta 1. Coerente com "cada ponto é julgado igual", e o desfazer da tela 25 reverte tudo. Registrado em `s6-side-out-on-the-deciding-point`.
- **Telas 08 → 25 → 09:** a tela 08 diz Pedro na 2 e Gabi na 1, e a tela 09 mostra o mesmo em 18–15 do 2º set. Essa conta não fecha pelas regras, porque o intervalo entre as zonas dos dois times não muda num set que o time que sacou primeiro vence. O golden começa em a1/b5 para fechar as telas 09, 10, 24 e 25. **Para a E4.7:** a tela 08 é ilustrativa; ajustar o dado se ela virar referência.
- **Tie-break com alvo diferente de 15:** "troca aos 8" (`rotacoes.md:39`) não diz o que fazer com outro alvo. Não afeta o motor: a E4.10 decide o desenho.
- **Tamanho do golden e dos testes:** 458 `MatchStarted` em `score-events.json` mudam. O script só expande a notação, e os esperados novos são regra simples por caso. O risco é o script copiar um erro do motor; ele não importa o motor, e os casos `s*` são independentes.
- **`matchInput` padrão com rotação desligada:** evita reescrever os testes do placar, mas esconde a rotação deles. Os testes de partida inteira com rotação usam a função nova da fixture.
- **E2.4, E2.5 e E2.7 mexem aqui:** `TeamState` e `MatchStarted` crescem, de novo com o golden. A E2.7 precisa do estado de cada ponto para a tela 24, porque `replayEvents` só devolve o final.
- **A citar no relatório do M2:** a exceção de D1; o lado da quadra fora do motor (D10); `lineup` ancorado no levantador; os limites sem mudança.
