# E4.2 · Cliente da API gerado, TanStack Query, tratamento de erro e offline

> **Nenhuma pergunta bloqueia o início.** Há **1 pergunta ao Gabriel** no fim do arquivo (o que a pessoa vê sem internet), com padrão adotado numa constante e num texto de `strings/`. Nada envolve conta nem gasto: o gerador e o cliente são MIT, sem serviço externo.
>
> **Sensível para segurança:** sim. O cliente manuseia o ID token do Firebase, decide para onde ele vai (só a origem da API, só HTTPS) e grava no aparelho um cache com nome de grupo, que pode ser dado pessoal. Desenvolvedor em **Opus** nas duas partes e `revisor-seguranca` em **cada parte** (a Parte 1 expõe ou não um documento que descreve a superfície da API).
>
> **Lacuna conhecida, para o orquestrador:** a pendência da E4.9 ("nomes dos jogadores offline") só fecha de verdade quando existir a API de perfil (E3.17, sugerida no plano da E3.2). A E4.2 entrega o cache persistido, a política do que entra nele e a porta que a quadra vai ler; os nomes reais entram nele quando a E3.17 acrescentar a rota, e a E4.7 troca o `CourtRoster` de exemplo pelo que lê o cache.

**Tarefa:** cliente da API gerado, TanStack Query, tratamento de erro e offline. **Aceite (`plano-mvp.md:157`):** "Tipos sempre iguais aos da API". **Depende de:** E3.1 (feita: `POST /v1/me`, ADR 0036). As rotas da E3.2 (grupos, membros, convites; ADR 0039 e 0040) já estão na `main` e entram no contrato. **Destrava:** E4.3 (login, que liga o `IdTokenProvider` real), E4.4, e, via E3.3 e E3.4, E4.5 e E4.6. A E4.11 usa o tratamento de erro e o `NetworkStatus` daqui, mas a fila de eventos dela é outra (D7).

**Branch:** `task/E4.2-api-client`, no worktree `D:\projetos\SacouAPP-E4.9`. Dois PRs (ver "Divisão em partes"); a Parte 2 sai de branch nova a partir da `main` atualizada (`task/E4.2-part2-app-client`).

**ADR:** o próximo número livre na `main` no momento do merge da Parte 1 (**0042**: o 0041 ficou com a E3.3). Título: "Contrato OpenAPI, tipos gerados no app, cliente HTTP e cache persistido". ## Decisões

### D1 · Como a API publica o contrato

- **`Microsoft.AspNetCore.OpenApi` 10.0.14** (mesmo patch do `Mvc.Testing` em `Directory.Packages.props`), referenciado só por `Sacou.Api`. Nada de Swashbuckle nem NSwag: o pacote é o da plataforma e lê os `Results<...>` tipados que os endpoints já declaram. O `Microsoft.OpenApi` transitivo fica fixado em `Directory.Packages.props` (versão que o 10.0.14 pede), para o `audit:api` ver a mesma coisa sempre.
- `builder.Services.AddOpenApi("v1", ...)` com transformadores numa pasta `apps/api/src/Sacou.Api/OpenApi/` (a API é o único lugar que conhece todos os módulos; os módulos não ganham referência nova). Documento em OpenAPI 3.1 (padrão do .NET 10), sem `servers` (não publica URL de ambiente nenhum).
- **O documento é um arquivo versionado:** `apps/api/openapi/v1.json`, LF, gerado pelo próprio teste (D3). É ele que o gerador TS lê. Ninguém edita à mão.
- **Transformadores** (cada um é uma classe pequena, com teste próprio):
  1. **Enums como texto.** O `ApiJson` usa um conversor próprio (`SingleValueEnumConverter`), que o gerador de esquema do .NET pode não reconhecer como texto (sairia `integer` ou esquema vazio). O transformador escreve `type: string` e `enum` com os valores **produzidos pelo mesmo `JsonSerializerOptions` do `ApiJson`** (serializa cada membro do enum e usa o resultado), para o documento nunca divergir do que a API realmente manda (`admin`, `coAdmin`, `scorekeeper`, `player`; `regular`, `dropIn`). Conferir primeiro o que o 10.0.14 já gera; o transformador só entra se precisar, mas o **teste** entra sempre.
  2. **`ProblemDetails` com `code`.** Esquema `ApiProblem` (`type`, `title`, `status`, `code` obrigatório, `traceId`), usado em toda resposta de erro de regra (ADR 0039: "o app traduz pelo `code`").
  3. **Respostas comuns.** Toda operação que exige login ganha 401 e 503 (`ProblemDetails`, com o cabeçalho `Retry-After` descrito no 503, ADR 0036 D7); toda operação com corpo ganha 400; toda operação com `RequestSizeLimitAttribute` ganha 413. As de regra (403, 404, 409 e o 400 de validação) vêm de cada endpoint: o `ProblemHttpResult` não diz o status, então cada endpoint declara `.ProducesProblem(...)` para os status que o handler pode devolver. Um teste de guarda (D3) reprova endpoint que devolve `ProblemHttpResult` sem nenhum `ProducesProblem`.
  4. **Catálogo de códigos de erro.** Extensão `x-sacou-error-codes` na raiz do documento, com todos os `code` de `Error` declarados como `static readonly` nos assemblies de módulo (`GroupErrors`, `CurrentUserErrors`, `UserErrors`, e os que vierem), por reflexão, em ordem alfabética. O gerador TS transforma a lista num tipo `ApiErrorCode` (D3), e o mapa de textos pt-BR é `Record<ApiErrorCode, string>`: código novo na API sem texto no app **não compila**.
- **`operationId`** vem do `WithName` que todo endpoint já tem (`SignIn`, `ListMyGroups`, `CreateGroup`, ...). Um teste reprova operação sem nome.
- **Requisição com `string?`:** os DTOs de entrada declaram `string? Name` para o domínio dar o erro com código (e não um 400 genérico do binding). No contrato o campo sai opcional e anulável; o app sempre o manda. Não mexer nos DTOs nesta tarefa.

### D2 · Exposição do documento

**Não fica exposto em produção, nem em nenhum ambiente publicado.** `app.MapOpenApi("/openapi/{documentName}.json").AllowAnonymous()` só quando `app.Environment.IsDevelopment()`. Justificativa: o documento lista todas as rotas, os campos e os códigos de erro; não é segredo (o app distribuído revela o mesmo a quem o desmontar), mas publicá-lo só facilita varredura, e ninguém de fora precisa dele. O app não baixa o documento em execução: os tipos são compilados.

- O teste de guarda das rotas anônimas (lista fechada do ADR 0040, D4) passa a aceitar `/openapi/{documentName}.json` **só** quando o ambiente é `Development`; em `Production` a lista continua a de hoje.
- Teste: com `Production`, `GET /openapi/v1.json` não é 200 (é 401 da `FallbackPolicy` ou 404; o teste aceita qualquer um dos dois e reprova 200).
- O teste que gera o arquivo (D3) sobe a API em `Development` pelo `WebApplicationFactory` que já existe em `Sacou.Api.Tests`. Se o 10.0.14 expuser um provedor público do documento por DI, o desenvolvedor pode usá-lo e dispensar o `MapOpenApi`; registrar no ADR qual caminho foi usado.

### D3 · Gerador TS e o portão do aceite

- **`openapi-typescript`** (MIT), versão **exata** em `devDependencies` de `apps/mobile` (sem `^` nem `~`, conferida pelo `pnpm install --frozen-lockfile`), gera `apps/mobile/src/api/generated/schema.ts` (`paths`, `components`, `operations`). Um script `scripts/generate-api-types.mjs` roda o gerador, escreve também `apps/mobile/src/api/generated/error-codes.ts` (`export const apiErrorCodes = [...] as const; export type ApiErrorCode = ...`) a partir de `x-sacou-error-codes`, e formata os dois com o Prettier do repositório. Os dois arquivos são versionados, com cabeçalho "generated, do not edit".
- **`openapi-fetch`** (MIT, mesmo autor, sem dependências de runtime), versão exata, é o cliente tipado pelos `paths`: o compilador recusa rota, método, parâmetro ou corpo que não existam no contrato.
- **A corrente que prova o aceite** (cada elo reprova a CI):
  1. `Sacou.Api.Tests/OpenApi/OpenApiContractTests.Document_matches_committed_file`: gera o documento da API real e compara, texto contra texto (JSON normalizado, LF), com `apps/api/openapi/v1.json`. Com `SACOU_UPDATE_OPENAPI=1` ele reescreve o arquivo em vez de comparar. Mudou um DTO e não regenerou: `dotnet test` vermelho.
  2. `pnpm check:api-types` (novo passo da CI, logo depois do `pnpm build`): roda o script sobre o `v1.json` versionado e falha se `git diff --exit-code apps/mobile/src/api/generated` mostrar diferença. Regenerou o JSON e não o TS: vermelho.
  3. `pnpm typecheck`: o cliente e as telas usam só os tipos gerados; campo renomeado na API quebra a compilação do app.
  4. `Record<ApiErrorCode, string>` nos textos: código novo sem tradução quebra o `typecheck`; código removido deixa uma chave a mais, que também quebra.
- **Atalho local:** `pnpm api:contract` = `SACOU_UPDATE_OPENAPI=1 dotnet test --filter OpenApiContract` + `generate-api-types`. Documentado em `CLAUDE.md` (Comandos) e `docs/padroes/codigo.md`.
- **Compatibilidade do `/v1` (ADR 0039, Consequências):** `scripts/check-openapi-compat.mjs`, sem dependência nova, compara o `v1.json` do PR com o da `origin/main` e reprova: rota ou método removido; campo removido de requisição; campo de requisição que passou a ser obrigatório; campo novo **obrigatório** em requisição; campo removido de resposta; valor removido de enum de resposta. Campo novo opcional e rota nova passam. Exceção só com a palavra `BREAKING-V1` no corpo do PR e ADR (o script lê o evento da CI). Passo `pnpm check:api-compat` na CI, com teste em `pnpm test:tooling`.
- **Exceções de qualidade** (`docs/padroes/codigo.md`): `src/api/generated/**` fora do ESLint, do `check:size` e do `check:duplication`, e dentro do `format:check`. O resto do app continua com as regras inteiras.

### D4 · Cliente no app: portas e adaptadores (`frontend.md`, regra 3)

Interfaces em `src/services/api/` (consumidas pelas fatias e pelos hooks, como o `FontLoader`); implementações em `src/adapters/`. Nenhuma tela, hook ou fatia importa `openapi-fetch` nem chama `fetch`: o ESLint passa a reprovar o global `fetch` e o import `openapi-fetch` fora de `src/adapters/` (casos novos em `lint:regression`).

| Porta | O que é | Real | Falsa |
|---|---|---|---|
| `SacouApi` | Um método por operação (`signIn`, `listMyGroups`, `createGroup`, `getGroup`, `renameGroup`, `listMembers`, `changeMemberRole`, `changeMemberType`, `removeMember`, `leaveGroup`, `createInvite`, `listInvites`, `revokeInvite`, `previewInvite`, `acceptInvite`), com tipos tirados de `components["schemas"]`, cada um devolvendo `Promise<ApiResult<T>>` (`{ ok: true, value } \| { ok: false, error: ApiError }`) | `http-sacou-api.ts` sobre `openapi-fetch` | `fake-sacou-api.ts`: em memória, com respostas programáveis por operação e registro das chamadas (sem o token) |
| `IdTokenProvider` | `getIdToken({ forceRefresh }): Promise<string \| null>` e `onSessionExpired(): void` | **E4.3** (Firebase). Aqui não há real | `fake-id-token-provider.ts`: token fixo, conta quantas vezes foi pedido e com `forceRefresh` |
| `HttpTransport` | `(request) => Promise<Response>`, o `fetch` injetado | `globalThis.fetch` dentro do adaptador | fila de respostas para os testes do cliente real |
| `NetworkStatus` | `isOnline()` e `subscribe(listener)` | `@react-native-community/netinfo` (versão do `bundledNativeModules` do SDK 58, via `expo install`) | interruptor manual |
| `KeyValueStore` | `getItem`, `setItem`, `removeItem` (contrato do persistidor do TanStack) | `sqlite-key-value-store.ts`, banco **separado** `sacou-cache.db` (D6) | `Map` em memória |

O cliente real sabe montar a requisição e ler a resposta, e mais nada: a decisão de repetir, renovar o token ou deslogar fica numa função pura testável (`api-policy.ts`), para o adaptador ficar pequeno.

**Configuração:** `src/services/api/api-config.ts` lê `EXPO_PUBLIC_API_URL` uma vez e valida: `https:` obrigatório; `http:` só com `__DEV__` e host `localhost`, `127.0.0.1`, `10.0.2.2` (emulador Android) ou IP privado da rede local. Sem barra final, sem caminho, sem credencial na URL, sem query. URL inválida é erro de inicialização com mensagem que cita a variável e nunca o valor. A URL não é segredo e não vai para `segredos.md`.

### D5 · Erros: `ApiError` e textos pt-BR

`ApiError` é uma união discriminada, sem corpo cru, sem cabeçalho e sem URL:

| `kind` | Quando | O que o app faz |
|---|---|---|
| `problem` (`status`, `code: ApiErrorCode`) | 400, 403, 404, 409 com `code` conhecido | Texto de `strings/api-errors.pt-BR.ts` pelo `code` |
| `session-expired` | 401 depois de **uma** renovação forçada do token e uma nova tentativa | `IdTokenProvider.onSessionExpired()` (a E4.3 desloga e limpa o cache, D6) |
| `not-registered` | 403 `identity.user-not-registered` (ADR 0039, D2) | Chama `signIn()` (`POST /v1/me`) e repete **uma** vez; se repetir, vira `problem` |
| `too-large` | 413 (o Kestrel responde sem `code`) | "Esse conteúdo é grande demais." |
| `unavailable` (`retryAfterMs`) | 503, com `Retry-After` em segundos ou data HTTP, limitado a 60 s; sem cabeçalho, 30 s | "O Sacou está fora do ar por um instante. Tentando de novo." Consulta repete depois do prazo (D6); mutação não |
| `offline` | Falha de rede, tempo esgotado (15 s, `AbortController`) | "Sem conexão." Consulta mostra o cache |
| `unexpected` (`status`) | 500, status não previsto, `code` desconhecido (app velho contra API nova), corpo que não é `ProblemDetails` | Texto genérico; `code` desconhecido nunca é mostrado nem logado como texto livre |

- **Ordem do 401:** o 401 sai do autenticador, antes de qualquer handler, então repetir uma mutação depois do 401 não a executa duas vezes. O mesmo vale para o 403 `not-registered` (sai do `ICurrentUser`, antes da escrita). É a única repetição permitida em mutação.
- **Renovação concorrente:** três consultas com 401 ao mesmo tempo pedem **uma** renovação (promessa compartilhada no cliente).
- **Grupo sumiu:** 404 `groups.group-not-found` em qualquer consulta do grupo remove a subárvore `["groups", groupId]` do cache e invalida `["groups"]` (quem foi removido ou saiu em outro aparelho deixa de ver o grupo, inclusive no cache persistido).
- **409:** mostra o texto e invalida a consulta do recurso, para a tela mostrar o estado novo.
- **Result pattern na fronteira do TanStack:** o `SacouApi` devolve `ApiResult`; só o `queryFn`/`mutationFn` desembrulha e lança o `ApiError` (é o contrato da biblioteca). Nada além disso lança erro de regra.
- Textos novos só em `apps/mobile/src/strings/api-errors.pt-BR.ts` (`Record<ApiErrorCode, string>` mais os de `kind`), coberto pelo `no-hardcoded-text.test.ts`.

### D6 · TanStack Query e cache persistido

- `@tanstack/react-query` e `@tanstack/react-query-persist-client` + `@tanstack/query-async-storage-persister` (MIT), versões exatas e iguais entre si.
- **Chaves** (`src/services/query/query-keys.ts`, fábrica tipada, nada de array literal nas fatias): `["me"]`, `["groups"]`, `["groups", groupId]`, `["groups", groupId, "members"]`, `["groups", groupId, "invites"]`. Nenhuma chave leva token, `userId`, token de convite nem texto digitado.
- **`staleTime`** (constantes nomeadas): lista de grupos 30 s; grupo e membros 60 s; convites 0 (só admin, muda com cada ação). `gcTime` de 7 dias nas chaves persistidas (tem de ser ≥ o `maxAge` do persistidor, senão o cache some antes de ser gravado). `refetchOnReconnect` ligado; foco pelo `AppState` (adaptador, `focusManager`); `onlineManager` ligado ao `NetworkStatus`.
- **Retentativa só no que é idempotente:** `shouldRetry(failureCount, error)` pura. Consultas (`GET`): até 2 vezes, só em `offline`, `unavailable` e `unexpected` com status 5xx; nunca em 4xx. `retryDelay` usa o `retryAfterMs` do 503; senão 1 s, 2 s. **Mutações: `retry: false`** sempre, inclusive `PUT` e `DELETE`, que a API trata como idempotentes (mudar papel para o mesmo valor é 200, revogar de novo é 204): a regra é simples e a pessoa toca de novo. Exceções: só as duas repetições do D5 (401 e `not-registered`), que acontecem antes de a API agir.
- **Mutações não fazem fila offline:** `networkMode: "always"` nas mutações, que falham na hora com `offline` em vez de ficar pausadas e rodar sozinhas depois (um `createGroup` pausado e perdido ao fechar o app, ou rodado horas depois, é pior que a mensagem). A única fila offline do app é a dos eventos da quadra (SQLite, E4.11).
- **Invalidação** (no `onSuccess` de cada mutação, em `src/services/query/invalidation.ts`, pura, testada): `createGroup` e `acceptInvite` → `["groups"]`; `renameGroup` → `["groups", id]` e `["groups"]`; papel, tipo, remover → `["groups", id, "members"]` (e `["groups"]` se o alvo é quem chama); `leaveGroup` → remove `["groups", id]` e invalida `["groups"]`; `createInvite` e `revokeInvite` → `["groups", id, "invites"]`.
- **Hooks entregues aqui** (para provar a corrente; as telas são das E4.4 e E4.5): `useMyGroups`, `useGroup`, `useGroupMembers`. Os dados ficam só no cache do Query (`frontend.md`, regra 1): nenhum `useState`, store ou contexto com cópia; o "tem dado velho?" é derivado de `dataUpdatedAt` e do `NetworkStatus`, nunca uma flag.
- **Onde fica o cache persistido:** um arquivo SQLite **separado**, `sacou-cache.db`, numa tabela `kv (key TEXT PRIMARY KEY, value TEXT NOT NULL) STRICT`, atrás do `KeyValueStore`. Nunca no `sacou.db` da quadra: o ADR 0038 garante, com teste sobre `pragma_table_info`, que o log da quadra não guarda nome, e o cache vai guardar. Sem AsyncStorage nem MMKV (dependência nativa nova sem ganho; o `expo-sqlite` já está no app). `android.allowBackup: false` (E4.9) já impede o backup automático de copiá-lo.
- **O que entra no cache persistido** (lista de permissão por prefixo de chave, `shouldDehydrateQuery`; o padrão é **não** persistir): `["groups"]`, `["groups", id]` e `["groups", id, "members"]`, só consultas com `status: "success"`; quando a E3.17 trouxer os nomes, a rota de perfis/nomes do grupo entra na lista (é o que a quadra precisa offline). **Nunca entra:** o ID token e qualquer cabeçalho; `["me"]` (`userId` interno, que o app não precisa guardar); `["groups", id, "invites"]` (autoria de convites, só para admin); a resposta de `createInvite` (o token do convite, que é mutação e nunca vai ao cache; o link gerado é da E4.5, no armazenamento seguro, ADR 0040); a prévia e o aceite do convite (mutações com o token no corpo); mutações em geral (`shouldDehydrateMutation: () => false`); erros.
- **Validade e troca de versão:** `maxAge` de 7 dias (constante, ver pergunta); `buster` = versão do app + hash do `v1.json` (gravado pelo gerador em `generated/`), para um cache gravado com tipos antigos ser descartado em vez de lido com a forma errada.
- **Troca de conta:** porta `clearSession()` (limpa o `QueryClient` e remove a chave do persistidor), chamada pela E4.3 no logout e no `session-expired`. Teste: depois de `clearSession`, o arquivo não tem nenhuma linha.
- **Sem criptografia do cache**, com justificativa no ADR: guarda nome de grupo e, depois, apelidos, que outros membros já veem; fica no sandbox do app; backup desligado. O `expo-secure-store` não serve para dezenas de KB. Rever se entrar dado sensível (nível, rating), que fica **fora** da lista de permissão.

### D7 · Segurança do cliente

- **O token só vai para a origem da API:** o cliente recebe só caminhos relativos do `paths` gerado e monta a URL sobre a `baseUrl` validada; o adaptador confere que a URL final tem a mesma origem antes de pôr o cabeçalho. `redirect: "manual"` (ou `"error"`) no `fetch`, para um redirecionamento nunca levar o `Authorization` a outro host; resposta 3xx vira `unexpected`. Conferir no Hermes se o `fetch` do React Native respeita a opção (ver Riscos); a API não redireciona nada hoje.
- **O token nunca vai para log nem para cache:** o adaptador não registra requisição nem resposta; `ApiError` não tem campo para cabeçalho, URL ou corpo; o token não é parâmetro de nenhuma função do Query; `fake-sacou-api` registra as chamadas sem o token. Testes: a serialização (`JSON.stringify`) de todo `ApiError` produzido e do estado desidratado do Query nunca contém o token de teste. O Sentry (E5.2) herda a regra pelo `beforeSend`, nota para lá.
- **HTTPS obrigatório:** D4 (validação da URL). O Android de release continua sem `usesCleartextTraffic` (padrão do Expo); um teste lê o `app.json` e reprova se alguém o ligar. Sem *certificate pinning*: a API fica atrás do certificado rotativo do Railway, e pinning errado derruba todo o app sem atualização possível; registrado no ADR e no modelo de ameaças.
- **Corpo de resposta:** lido como JSON só com `Content-Type` `application/json` ou `application/problem+json`; outro tipo vira `unexpected`. Sem validação de esquema em execução (os tipos são de compilação); o que a tela mostra é texto do React Native, sem HTML.

## Riscos

- **Enum com conversor próprio:** o gerador de esquema do .NET 10 pode descrever errado o `SingleValueEnumConverter`. Mitigação: C3, que compara com a serialização real. Se o transformador não bastar, trocar por esquema escrito por tipo, mantendo o teste.
- **`ProducesProblem` à mão por endpoint:** um status esquecido não aparece no contrato. A guarda C7 só pega a ausência total. Mitigação parcial: o app trata qualquer `problem` com `code` conhecido, mesmo de status não declarado, porque o catálogo de códigos é global.
- **`fetch` do React Native e `redirect`:** o RN pode ignorar `redirect: "manual"`. Conferir no Hermes no roteiro da E4.3; se ignorar, o adaptador recusa resposta cuja `url` final mude de origem (o risco real hoje é nulo: a API não redireciona e o Railway só redireciona HTTP→HTTPS, que a URL validada já evita).
- **NetInfo é módulo nativo novo:** exige novo APK de teste; o roteiro da E4.3 inclui "modo avião abre a lista de grupos do cache". Se o build falhar, alternativa sem nativo: `onlineManager` pelo resultado das próprias requisições (perde o aviso imediato de volta da rede).
- **Teste de contrato e o `WebApplicationFactory`:** sobe a API com a configuração de teste (banco, Firebase); se o `Program` exigir banco para gerar o documento, usar a mesma configuração dos testes HTTP existentes, sem `MigrateOnStartup`.
- **Nomes offline dependem da E3.17** (topo). A quadra continua com o `CourtRoster` de exemplo até a E4.7.
- **Tamanho:** se a Parte 2 passar de um ciclo, separar o persistidor e o `NetworkStatus` (offline) do cliente e dos erros.
