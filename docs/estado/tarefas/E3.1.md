## Decisões

### D1 · Validar o ID token como JWT pelas chaves públicas do Google, sem FirebaseAdmin (ADR 0036)

A API confere o ID token conforme a seção "Verify ID tokens using a third-party JWT library" da documentação do Firebase, com `Microsoft.IdentityModel.JsonWebTokens` (Microsoft, já usado pelo JwtBearer). As chaves vêm da URL documentada `https://www.googleapis.com/robot/v1/metadata/x509/securetoken@system.gserviceaccount.com`.

Por que não o FirebaseAdmin para validar (o ADR 0014 e `produto.md:250` diziam FirebaseAdmin):

1. **O Admin SDK exige conta de serviço** para inicializar, mesmo quando só verifica token, segundo a documentação. Pelo caminho JWT, a E3.1 precisa só do ID do projeto, que é público: nenhum segredo nesta tarefa.
2. **Testável sem rede:** a busca de chaves do FirebaseAdmin não pode ser trocada por fora. Aqui, os testes assinam tokens com uma chave RSA local e servem as chaves por um `HttpMessageHandler` falso (abordagem aprovada pelo Gabriel).
3. **Menos dependências:** sem `Google.Apis.Auth` nem a árvore do Gax para auditar.
4. **O que se perde:** o `checkRevoked`. A documentação diz que `verifyIdToken()` não confere revogação, e o `checkRevoked` faz uma chamada de rede a cada uso. Risco aceito, com mitigação na E3.16 (ver Riscos).

**O FirebaseAdmin continua na stack (`decisoes.md:25`)** para administrar contas: apagar o usuário no Firebase na E3.16. Lá entra `SACOU_FIREBASE_SERVICE_ACCOUNT` (D8).

**A interface que permite trocar:** `IIdTokenVerifier.VerifyAsync(string token, CancellationToken) → Task<Result<VerifiedLogin>>` (interna ao Identity, pasta `Authentication/`). `VerifiedLogin(AuthSubject Subject, SignInProvider Provider)` não cita o Firebase. O handler de autenticação e a fatia só conhecem a interface. Trocar para o FirebaseAdmin é registrar outra implementação no DI. Domínio, fatia e testes de HTTP não mudam. As chaves também ficam atrás de uma interface (`ISigningKeySource`), trocada nos testes de unidade.

### D2 · Regras de aceitação do token (ADR 0036)

Todas as regras vêm da documentação do Firebase. As do item "Endurecimento" são escolha nossa.

| Regra | Como |
|---|---|
| `alg` = `RS256`, e só ele | `ValidAlgorithms = ["RS256"]`. Recusa `none`, HS256 (inclusive "assinado" com a chave pública como segredo), RS512, PS256 e ES256 |
| `kid` obrigatório e conhecido | `IssuerSigningKeyResolver` próprio, que devolve **só** a chave daquele `kid`. `TryAllIssuerSigningKeys = false`. Sem `kid` ou `kid` desconhecido: recusa. Cabeçalhos `jwk`, `jku` e `x5u` são ignorados, e nunca há busca de chave fora da URL fixa |
| Assinatura | `RequireSignedTokens = true` |
| `aud` = ID do projeto, string única | Validador próprio: lista com valores extras ou `aud` ausente: recusa |
| `iss` = `https://securetoken.google.com/<projectId>` | Comparação exata (sem barra final, sem `http`, sem `accounts.google.com`) |
| `exp` no futuro, `iat` e `auth_time` no passado | Função pura `FirebaseTokenRules.CheckTimes(claims, now)` com tolerância de **60 s** (constante `ClockSkew`). Campo ausente: recusa. `nbf`, se vier, também é conferido. A validação de tempo da biblioteca continua ligada como segunda barreira. Se o `TokenValidationParameters` da versão usada aceitar `TimeProvider`, passe o mesmo relógio (o desenvolvedor confere) |
| `sub` | String de 1 a 128 caracteres ASCII visíveis (0x21 a 0x7E). 128 é o limite de UID do Firebase. Vira o value object `AuthSubject` |
| **Endurecimento:** provedor | `firebase.sign_in_provider` precisa estar em `password`, `google.com` ou `apple.com`. Recusa `anonymous`, `phone` e `custom`: sem telefone (`decisoes.md:19`), e um provedor ligado por engano no console não cria conta |
| **Endurecimento:** sem tenant | `firebase.tenant` presente: recusa (o projeto não usa multilocação) |
| **Endurecimento:** tamanho e formato | `MaximumTokenSizeInBytes` = 8 KB (um ID token tem cerca de 1 KB). JWE (5 partes) recusado, porque não há chave de decriptação |
| **`email_verified`: não é exigido** | Ver D3 |

**Erros:** o motivo da recusa é um enum interno (`IdTokenRejection`), registrado em log só como categoria (`Expired`, `UnknownKey`...). Nunca vai para a resposta: o 401 é sempre igual, para não servir de oráculo. `IncludeErrorDetails` não existe neste handler, e o `WWW-Authenticate` é só `Bearer`. `IdentityModelEventSource.ShowPII` e `LogCompleteSecurityArtifact` nunca são ligados. A mensagem de exceção da biblioteca nunca é registrada, porque pode ecoar partes do token.

### D3 · E-mail não verificado é aceito, e a API não usa nem guarda e-mail (ADR 0036)

- **Motivo:** a identidade é o `sub` (UID do Firebase), nunca o e-mail. A API não liga contas por e-mail. Exigir verificação poria uma tela "confirme seu e-mail" no caminho da meta de menos de 45 s (`produto.md:115`), o que muda o que o usuário vê. Por isso fica a pergunta 1, com este padrão adotado até a resposta.
- **Consequência registrada para a E3.5:** reivindicar convidado nunca usa coincidência de e-mail, só o link (`revisao-mvp.md:114`).
- **Risco residual:** alguém cria conta de e-mail e senha com o e-mail de outra pessoa. Como a API não usa o e-mail, o efeito é limitado: quando o dono entra com Google pelo mesmo e-mail, o Firebase (com a configuração padrão de uma conta por e-mail) torna o Google o provedor confiável e tira a senha, e o invasor perde o acesso.

### D4 · Senha e tentativas repetidas ficam com o Firebase (fecha a pendência do ADR 0014)

A senha nunca passa pela API: o app fala direto com o Firebase Auth, que tem bloqueio próprio por excesso de tentativas (`auth/too-many-requests`) e proteção contra enumeração de e-mails, ligada por padrão em projetos criados depois de 15/09/2023. O que chega à API é o token já emitido. O limite de requisições do `POST /v1/me` fica para a E5.3, como já previsto. A senha mínima é a padrão do Firebase, 6 caracteres (resposta do Gabriel, 08/11/2026): nada a ajustar no console.

### D5 · Usuário × `MemberId` (ADR 0036, cumpre o ADR 0012)

- **A E3.1 cria só o `User`** (módulo Identity): `UserId` interno (UUID v7, `Guid.CreateVersion7()`, gerado pela API), `AuthSubject` (UID do Firebase) e `CreatedAt`. O UID do Firebase não é a chave interna: assim, trocar de provedor ou apagar a conta (E3.16) não espalha o UID por outras tabelas.
- **`MemberId` nasce na E3.2,** quando a pessoa entra num grupo: um `User` tem 0..n `MemberId` (um por grupo), e o convidado tem `MemberId` sem `User`. Eventos e histórico só apontam para `MemberId` (ADR 0012). A ligação `MemberId → UserId` fica no Groups, com tipo e lugar decididos na E3.2. O `UserId` da E3.1 é `internal` no Domain do Identity. A E3.2 decide como expô-lo em `Identity.Contracts`, por exemplo um `ICurrentUser`, já que o Domain não pode usar o namespace `Contracts`.
- **Dados guardados (minimização):** só `id`, `firebase_uid` e `created_at`. **Não são guardados:** e-mail, `email_verified`, nome e foto do Google ou da Apple, provedor, IP, horário do último login, token. Um teste de modelo trava as 3 colunas: acrescentar uma exige mudar o teste e `dados-pessoais.md`.

### D6 · Primeiro login idempotente com uma instrução só (ADR 0037)

`POST /v1/me` faz, nesta ordem:

1. `SELECT id FROM identity.users WHERE firebase_uid = @sub`. É o caminho comum, de quem volta.
2. Se não achou: `INSERT … VALUES (@id, @sub, @now) ON CONFLICT (firebase_uid) DO NOTHING RETURNING id`.
3. Se o `INSERT` não devolveu linha (outro login venceu a corrida): repetir o `SELECT`.

O índice único em `firebase_uid` é a garantia. A criação é atômica no Postgres, sem exceção como fluxo. Só quem inseriu recebe **201**; os outros recebem **200**, e todos com o mesmo `userId`. SQL sempre parametrizado (interpolação do EF, que vira parâmetro). A comparação de UID é sensível a maiúsculas: UIDs do Firebase diferenciam caixa, e `text` com a collation padrão faz o mesmo.

### D7 · Endpoint, autenticação e erros: primeiro endpoint da API (ADR 0036)

- **Rota:** `POST /v1/me`, sem corpo. Resposta `{ "userId": "<uuid>" }`, com 201 (criado) ou 200 (já existia). O prefixo `/v1` fica decidido aqui. `GET /v1/me` (perfil) é da E4.3.
- **Handler próprio** `FirebaseAuthenticationHandler : AuthenticationHandler<…>`, esquema `IdentityModule.AuthenticationScheme`. Lê **só** o cabeçalho `Authorization: Bearer <token>`, com um único cabeçalho; nunca lê query string nem cookie. Monta o `ClaimsPrincipal` com uma claim só, o `sub` (`ClaimTypes.NameIdentifier`). E-mail e nome do token nunca entram no principal.
- **Seguro por padrão:** `FallbackPolicy` = usuário autenticado. Todo endpoint novo exige login, salvo `AllowAnonymous` explícito. `/health` ganha `AllowAnonymous`.
- **Respostas:** `AddProblemDetails()` com `UseStatusCodePages()` e `UseExceptionHandler()`. 401 com corpo `ProblemDetails` padrão e `WWW-Authenticate: Bearer`, sem motivo. Chaves do Google indisponíveis e nenhuma em cache: **503** com `Retry-After`, para o app não deslogar a pessoa por falha do Google. Erro inesperado: 500 sem detalhe.
- **Desvio registrado do ADR 0005:** o mapeamento `Result → ProblemDetails` "vem com o primeiro endpoint", mas este não tem erro de regra de negócio, só 401, 503 e 500, que vêm do pipeline. **O mapeamento entra na E3.2**, o primeiro endpoint com erro de regra. O lugar dele precisa de ADR, porque módulo não pode depender de `Sacou.Api` (`ModuleBoundaryViolations`).
- **Sem CORS** (app nativo; a página web da E3.12 é da mesma origem). **Sem OpenAPI nesta tarefa:** a E4.2 liga o gerador. O endpoint já declara `TypedResults` e `.WithName("SignIn")`, para o documento sair certo.

**Formato de `SACOU_FIREBASE_SERVICE_ACCOUNT` (para a E3.16):** o JSON baixado do console, **codificado em Base64 padrão, numa linha só, sem aspas**. O JSON tem várias linhas e o campo `private_key` tem `\n` escapados: em `.env` com aspas duplas, o `\n` vira quebra de linha e o JSON fica inválido, e Railway e GitHub tratam valores de várias linhas de jeitos diferentes. Base64 é igual em `.env`, Railway e GitHub Actions. A E3.16 decodifica, valida que é JSON com `type = service_account` e `project_id` igual a `Firebase:ProjectId`, e nunca registra o valor nem o erro de parse. **GitHub Actions: não cadastrar.** Nenhum job usa a chave, e os testes usam chaves locais.

### D9 · EF Core por módulo (ADR 0037)

- Um `DbContext` por módulo, `internal`, em `<Module>/Infrastructure/`. Schema próprio (`identity`), com o histórico de migrações no próprio schema (`MigrationsHistoryTable("__ef_migrations_history", "identity")`). Nomes em snake_case explícitos (`ToTable`, `HasColumnName`), sem pacote de convenção. O Domain não tem atributo de EF: o mapeamento fica em `IEntityTypeConfiguration` na Infrastructure.
- Pacotes centrais: `Npgsql.EntityFrameworkCore.PostgreSQL` 10.0.x, alinhado ao `Npgsql` 10.0.3 já fixado; `Microsoft.EntityFrameworkCore.Design` com `PrivateAssets="all"`, só para gerar migrações; `Microsoft.IdentityModel.JsonWebTokens` 8.x (a mais recente; versões antigas tiveram CVE); `Microsoft.AspNetCore.TestHost` 10.0.14 nos testes. `dotnet-ef` em `.config/dotnet-tools.json`, com versão exata. `IDesignTimeDbContextFactory` no próprio módulo, para gerar a migração sem depender da API.
- Migrações aplicadas por `IdentityModule.MigrateAsync(IServiceProvider)` (método público na classe de entrada, que a regra de superfície permite), chamado pelo `Program` quando `Database:MigrateOnStartup` for `true`, e pela fixture de integração.
- **Migrações são código gerado:** `.editorconfig` com `generated_code = true` em `**/Infrastructure/Migrations/*.cs`, e exclusão no `jscpd`, porque o `*.Designer.cs` e o `ModelSnapshot` repetem o mesmo modelo (ver "Portões da E0.10"). O namespace segue a pasta (`IDE0130`).

## Riscos

- **Sem conferência de revogação:** um token emitido antes de bloquear ou apagar a conta vale por até 1 h (validade do ID token). **Para a E3.16:** apagar a linha sozinho não basta, porque o mesmo token, ainda válido, recriaria o usuário no `POST /v1/me`. A E3.16 grava uma marca de exclusão do UID, ou recusa `auth_time` anterior à exclusão, ou usa `checkRevoked` só nesse endpoint. Registrar no ADR 0036 e em `progresso.md`.
- **Endpoint de chaves do Google:** usamos só a URL documentada. Mudança de formato derruba o login (503, não 401, então o app não desloga). K1 e K4 cobrem o comportamento.
- **ID do projeto errado em `appsettings.json`:** todo login real dá 401. Só aparece na E4.3, e o roteiro acima pega.
- **Relógio do servidor:** tolerância de 60 s; Railway sincroniza por NTP.
- **Primeiro EF Core e primeiro endpoint:** os padrões (ADR 0037, `/v1`, `FallbackPolicy`, `ProblemDetails`) viram precedente para todos os módulos. O revisor lê com esse peso.
- **Tamanho da tarefa:** é grande para um ciclo. Commits por passo; se o revisor pedir, dividir o PR em (a) domínio, autenticação e testes e (b) EF, fatia e integração, sem mudar o plano.
- **`Microsoft.IdentityModel` com CVE no futuro:** coberto pelo `audit:api` e pelo Dependabot.
- **E-mail não verificado aceito (D3):** depende de nenhuma tarefa futura ligar contas por e-mail. Fica registrado no ADR e no modelo de ameaças.
- **Apple:** o provedor no console exige conta Apple Developer (paga), o que já é necessário para publicar no iOS. Não afeta a E3.1, que só aceita `apple.com`; o custo é decisão da E4.3/E5.4.
