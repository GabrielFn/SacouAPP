## 2. Decisões

| Tema | Decisão | Base |
|---|---|---|
| Primeiro evento | **`MatchStarted`** abre o stream, já com o set 1 aberto em 0–0. Qualquer outro evento sem partida aberta é `event-rejected`; `RevertedTo` como primeiro evento já é `invalid-revert-target`. Desfazer o primeiro ponto volta ao `MatchStarted`. Sem evento vazio de "abrir quadra": a E2.6 cria um se a fila precisar | `eventos.md:36`; `revisao-mvp.md:106` |
| `rulesVersion` | Inteiro ≥ 1 no `MatchStarted`, guardado na partida. **O replay aceita qualquer versão**, pois o resultado está gravado; só os comandos recusam versão não suportada | `decisoes.md:26`; ADR 0009 |
| Cópia congelada | `scoring` por valor no `MatchStarted`, todos os campos obrigatórios e sem padrão no motor (o SettingsResolver resolve antes). O aplicador lê do evento, nunca de constante. Formações só na E2.4, quando houver quem leia | `eventos.md:17`; E2.1 |
| Sets | `bestOf`: 1, 3 ou 5. Sets para vencer: `(bestOf + 1) / 2` | Telas 08, 20 |
| Pontos | `pointsPerSet` e `tieBreakPoints` de 1 a 99 (limite técnico, dois dígitos no placar); `tieBreakPoints: null` desliga o tie-break | Tela 08; `produto.md:75` |
| Tie-break | Só no set decisivo: `bestOf > 1`, `setNumber === bestOf` e valor não nulo. **Com 1 set, vale `pointsPerSet`**, porque a tela 18 mostra "25 pontos · 1 set · tie-break 15" | Telas 08, 18 |
| Vantagem | `winMargin`: 2 (vantagem de 2) ou 1 (sem vantagem). Vale também no tie-break. **Sem teto** de pontos: nenhum documento prevê | Tela 18; `produto.md:69` |
| Fim de set | Sempre confirmado: a regra só detecta; `SetEnded` nasce da confirmação. Com o set decidido e sem confirmar, `scorePoint` devolve `set-decided` | `produto.md:69`; tela 25 |
| Só resultado no evento | `SetEnded` grava o vencedor e o alvo do próximo set; `MatchEnded`, o vencedor. O aplicador confere a estrutura (partida, set, set aberto) e **não recalcula regra**: `SetEnded` em 10–8, ou com o vencedor atrás, é aplicado como gravado | ADR 0009; `eventos.md:56` |
| Ponto sem placar absoluto | `PointScored` grava o time e o aplicador soma 1. Com placar absoluto e conferência, dois escritores intercalados travariam o stream, o que `eventos.md:66` proíbe. `matchId` e `setNumber` barram o ponto atrasado de outro set, em vez de contá-lo no set errado | `eventos.md:66` |
| Fim de partida | Dois eventos da mesma confirmação: `SetEnded` com `nextSet: null` e `MatchEnded`, gravados juntos pelo chamador. Se só o primeiro gravar, o estado fica sem set aberto e `confirmSetEnd` emite o `MatchEnded` que falta | Telas 11, 25 |
| Chaves | Só `a`, `b` e nomes do esquema. **Sets e times em arrays, nunca em chave numérica nem por ID.** Parser fechado recusa `"1"`. Estado monta chaves em ordem UTF-16 crescente, porque o golden compara o texto | ADR 0022 |
| Versão do esquema | E2.3 e seguintes acrescentam campos ao `MatchStarted` e ao `nextSet` ainda em `schemaVersion` 1, atualizando o golden; nada foi gravado em produção. Com dados reais, muda a versão | Decisão técnica |
| Nome | Tipo do set é `MatchSet`, para não colidir com o `Set` do JS. Lados `a`/`b` (`TeamSide`), como as etiquetas das telas. `MemberId` é apelido de `string` aqui; o local do tipo fica na E3.2 | `produto.md:283-290`; ADR 0012 |

### Payloads (schema 1)

| Tipo | Payload |
|---|---|
| `MatchStarted` | `{ matchId, rulesVersion, scoring: { bestOf, pointsPerSet, tieBreakPoints, winMargin }, teams: { a: { memberIds }, b: { memberIds } } }` |
| `PointScored` | `{ matchId, setNumber, team }` |
| `SetEnded` | `{ matchId, setNumber, winner, nextSet: { targetPoints } \| null }` |
| `MatchEnded` | `{ matchId, endReason: "sets-won" \| "manual", winner: "a" \| "b" \| null }` |

- `matchId` e `memberIds` em UUID minúsculo. `memberIds`: de 1 a 24 por time (limite técnico, acima de qualquer time com banco), sem repetir dentro do time nem entre times. A ordem é preservada. Nenhum texto livre: o nome e a cor do time ficam fora do evento.
- `setNumber` de 1 a 5. Em `MatchEnded`, `sets-won` exige `winner` não nulo e nenhum set aberto (senão `event-rejected`). `manual` aceita `null`, inclusive para placar desligado.
- O `MatchStarted` é rejeitado com partida aberta ou `matchId` repetido no stream.
- **Erro:** `{ code: "invalid-payload", field }`. `field` é caminho do esquema (`scoring.bestOf`), `payload` ou `unknown-field`, nunca valor nem chave recebida. Desconhecido é conferido primeiro; depois, a ordem da tabela. No replay, vira `event-rejected`.
- Inteiros com `Number.isSafeInteger`, chaves com `Object.hasOwn`. `__proto__`, `constructor` e `"1"` no payload são `unknown-field`.

### Estado (chaves na ordem real)

```
CourtSessionState { currentMatch: MatchScore | null, finishedMatches: FinishedMatch[] }  // inicial: null, []
MatchScore { completedSets: [{ score, setNumber, winner }], currentSet: { score: { a, b }, setNumber, targetPoints } | null,
             matchId, rulesVersion, scoring, setsWon: { a, b }, teams }
FinishedMatch: MatchScore + endReason (depois de currentSet) + winner (no fim). O set em andamento fica em currentSet.
```

## 5. Riscos e perguntas em aberto

- **Servidor confia no resultado:** o evento prova formato, não verdade. `SetEnded` falso passa no replay, e `MemberId` em UUID válido pode não ser do grupo. A E3.7 confere membros contra o grupo e simula o replay; se validar `SetEnded` pela regra, usa as funções portadas. Citar em `modelo-de-ameacas.md`. Quem tem token de placar já pode marcar qualquer ponto, então isso não dá poder novo.
- **Ponto atrasado travando o stream:** ponto de set já encerrado é `event-rejected`, e com falha fechada trava o recálculo. Coerente com a E2.1: a E3.7 e a E4.9 rejeitam antes de persistir, e pontos do mesmo set intercalam sem erro. **Passar à E3.7:** com a ordem por `batch`, um evento anterior ao `MatchStarted` também trava.
- **`MemberId` em UUID:** presume que a E3.2 gere UUID minúsculo; se não, o parser muda.
- **Placar sem teto:** dois times nivelados em vantagem nunca são cortados. Sem queixa prevista; `docs/ideias.md` se surgir.
- **E2.3 mexe aqui:** acrescenta `firstServer` e o setup por time, com a tela 25 ("troca de lados e o Azul começa sacando"), e soma lógica ao `PointScored`. Conflito esperado no `SCORE_APPLIERS` e no golden. O plano da E2.3 decide se o side-out vai no mesmo evento ou em evento próprio.
- **Decisões a citar no relatório do M2:** limites de 1 a 99 e 24 membros, `winMargin` 1 ou 2 e o mesmo valor no tie-break, sem teto.
