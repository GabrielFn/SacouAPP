# ADR 0068 · Deploy no Cloud Run e no Neon

**Status:** aceito (18/11/2026), E5.1. **Decidido por:** Gabriel (troca do Railway pelo Google Cloud Run, 18/11, e respostas 87, 89 a 95 de `perguntas.md`) e desenvolvedor, dentro da arquitetura aprovada. **Substitui em parte:** a linha "Hospedagem: Railway Hobby" do [ADR 0008](0008-stack-backend-app-services.md) e de `visao-geral.md`.

## Contexto

A API precisava subir para teste e produção com deploy automático a partir da `main` (aceite da E5.1) e com o banco no Neon, Postgres 18 (ADR 0020). O Railway Hobby custa US$ 5 por mês; o Gabriel trocou pelo Cloud Run para ter custo zero no piloto. A infraestrutura (projeto, contas, federação, segredos) foi criada uma vez pelo Gabriel no Cloud Shell com `scripts/gcp/setup-sacou-api.sh` ([`gcp-configuracao.md`](../../operacao/gcp-configuracao.md)). O plano completo, com a pesquisa e o que não foi confirmado, está em `docs/estado/tarefas/E5.1.md`.

## Decisão

1. **D1 · Imagem própria.** `Dockerfile` na raiz, com contexto na raiz e um `.dockerignore` fechado por padrão (abre só `apps/api/src/`, os dois JSON embutidos pelos módulos e os arquivos de build da raiz; fecha de novo `bin`, `obj`, `node_modules` e `.env*`). Build com `mcr.microsoft.com/dotnet/sdk:10.0.403-noble` (o SDK do `global.json`), `dotnet restore --locked-mode` e `dotnet publish -c Release`; execução com `aspnet:10.0.14-noble-chiseled` (sem shell, sem gerenciador de pacotes, menor para os 0,5 GB do Artifact Registry). As duas imagens fixadas por digest; `USER $APP_UID` explícito; porta `ASPNETCORE_HTTP_PORTS=8080`. **ReadyToRun fica desligado** até a medição da partida a frio (caso 22 do plano), que só dá para fazer no ambiente: se a primeira requisição passar de 10 s, ele é a primeira opção a medir.
2. **D2 · Um projeto (`sacou-api`), dois serviços na `us-east4`** (respostas 92 e 93): `sacou-api-test` (`Staging`) e `sacou-api` (`Production`). Cada um com 1 vCPU, 512 MiB, concorrência 80, **`maxScale` 1** (o limitador da E5.3a vive na memória do processo), `minScale` 0 (resposta 90), cobrança por requisição (`cpu-throttling`), *startup CPU boost*, tempo limite de 60 s e sonda de partida HTTP em `/health` (5 s × 24 falhas = 2 min para migrar). A CPU fica parada fora das requisições: a API não tem `IHostedService` nem `BackgroundService`, e o teste de arquitetura `DeploySetupTests.Api_HasNoBackgroundWork` proíbe os dois enquanto valer essa cobrança.
3. **D3 · Uma conta por job, com o mínimo, sem chave JSON.** O GitHub Actions assume as contas por **Workload Identity Federation**. A primeira versão tinha uma só, `sacou-deployer` (`run.developer` no projeto e `serviceAccountUser` nas duas contas de execução, para qualquer workflow da `main`): a aprovação da produção só existia no GitHub, e um `deploy-api.yml` alterado e mergeado publicaria `sacou-api` sem o ok do Gabriel ou subiria o teste como `sacou-api-run`, lendo o banco de produção (revisão de segurança, achado S1). Agora são três (`scripts/gcp/harden-deploy-identities.sh`, que apaga a antiga):
   - `sacou-builder`: só `roles/artifactregistry.writer` no repositório `sacou`; `workloadIdentityUser` só para o *subject* `repo:GabrielFn@5855069/SacouAPP@1440184485:ref:refs/heads/main`, que o GitHub dá a um job **sem** ambiente (o `build`).
   - `sacou-deployer-test`: só `roles/run.developer` **no serviço** `sacou-api-test`, `roles/artifactregistry.reader` no repositório `sacou` (o Cloud Run confere que quem publica consegue ler a imagem) e `roles/iam.serviceAccountUser` só em `sacou-api-test-run`; *subject* `repo:GabrielFn@5855069/SacouAPP@1440184485:environment:test`.
   - `sacou-deployer-prod`: o mesmo para `sacou-api` e `sacou-api-run`; *subject* `repo:GabrielFn@5855069/SacouAPP@1440184485:environment:production`. Só um job no ambiente `production`, que exige a aprovação do Gabriel, recebe esse *subject*: a aprovação passa a valer também do lado do Google.
   - **Papel por serviço, não no projeto.** Um papel não se concede num serviço que ainda não existe, e `run.services.create` só existe no projeto (ou acima); com `run.developer` no projeto, qualquer deployer mexeria nos dois serviços. Por isso o script **cria os dois serviços** com a imagem pública de exemplo do Google (`us-docker.pkg.dev/cloudrun/container/hello`), cada um com a sua conta de execução, e só então concede `run.developer` em cada um. O deploy usa `gcloud run services replace`, que num serviço existente só precisa de `get` e `update` nele. O script também liga o acesso público (`allUsers` com `run.invoker`), antes uma caixa do console; nenhuma conta de deploy tem `run.admin` nem acesso a segredo.
   - **Por *subject* e não por atributo de ambiente:** o `google.subject` já é mapeado de `assertion.sub` e sempre existe; um `attribute.environment` mapearia um *claim* que o job `build` não tem. Vale o formato padrão do *subject* do GitHub; se o repositório personalizar o *subject* do OIDC, as três ligações têm de mudar.
   - O provedor `sacouapp` do pool `github` aceita só `assertion.repository_id == '1440184485' && assertion.ref == 'refs/heads/main' && assertion.workflow_ref == 'GabrielFn/SacouAPP/.github/workflows/deploy-api.yml@refs/heads/main'` (o `workflow_ref` também é mapeado em `attribute.workflow_ref`). Outro workflow da `main` não troca token nenhum.
   - O que sobra: um `deploy-api.yml` alterado e mergeado ainda publica no **teste** sem revisão, e o builder pode enviar uma imagem qualquer, que só chega à produção pela aprovação. Aceito.
   - `sacou-api-test-run` e `sacou-api-run` executam cada serviço e leem só o próprio segredo. Provedor, conta e projeto ficam em variáveis do repositório (`vars.GCP_*`), que não são segredo: a CI continua sem segredo (ADR 0004).
4. **D4 · Workflow separado, `.github/workflows/deploy-api.yml`.** Disparo por `workflow_run` do `CI` (`completed`, `main`); só segue com `conclusion == 'success'`, `event == 'push'`, `head_branch == 'main'` e o repositório de origem igual a este. `permissions: contents: read` no workflow e `id-token: write` só nos três jobs que falam com o Google (`build`, `deploy-test`, `deploy-production`), cada um com a sua conta (`vars.GCP_BUILDER_SA`, `vars.GCP_DEPLOYER_TEST_SA`, `vars.GCP_DEPLOYER_PROD_SA`; teste de arquitetura). `concurrency` em cada deploy (`deploy-api-test` e `deploy-api-production`), sem cancelar, e não no workflow: um run à espera da aprovação da produção não trava o deploy do teste do run seguinte. Ações fixadas por SHA; depois do `auth`, nenhum build nem ação de terceiros, porque o arquivo de credencial fica na workspace.
   - **Deploy só quando muda algo da API:** o job `changes` passa o `git diff` do commit contra o primeiro pai (o merge é squash) para `scripts/ci-areas.mjs`; com `api=false` (só `docs/` fora de `docs/dominio/`, ou só `apps/mobile/`) o deploy é pulado; diff vazio ou com erro faz o deploy. Testado em `scripts/lib/ci-areas.test.mjs` ("API deploy decision").
   - `build` monta a imagem **antes** de autenticar (nenhuma credencial chega ao contexto), envia para `us-east4-docker.pkg.dev/sacou-api/sacou/api:<sha>` e devolve a referência **por digest**.
   - `deploy-test` (ambiente `test`) e `deploy-production` (ambiente `production`, com o Gabriel como revisor obrigatório, resposta 87) usam a ação local `.github/actions/deploy-cloud-run`, **a mesma imagem pelo digest**, e terminam com `curl` em `/health`. A produção só sobe depois do `/health` do teste e da aprovação: essa aprovação é o ok explícito de cada deploy em produção.
   - **Desvio do plano:** em vez de `deploy-cloudrun` com `env_vars` e `secrets`, a ação aplica `deploy/cloud-run/service.yaml` com `gcloud run services replace`. O arquivo declara tudo do D2 (inclusive a sonda de partida: não ficou confirmado que as flags de sonda do `gcloud run deploy`, usadas pelo `deploy-cloudrun`, estejam no GA; o YAML do serviço é o formato estável) e o segredo só por `secretKeyRef`. O `envsubst` troca só nomes listados, e a ação recusa uma imagem que não seja `.../sacou/api@sha256:<64 hex>`. O teste de arquitetura confere `maxScale` 1, o caminho da sonda igual ao `MapHealthChecks` do `Program.cs`, o segredo por referência e a cobrança por requisição.
5. **D5 · Conexão a partir de `SACOU_DATABASE_URL`.** Antes dos módulos, `DatabaseConnectionSetup` (raiz da API) converte a URL do Neon em `ConnectionStrings:Sacou` com `DatabaseUrl.ToConnectionString`, função pura que devolve `Result`. Só converte se a connection string estiver vazia (o desenvolvimento local não muda). Força `SSL Mode=VerifyFull`; aceita só `sslmode` e `channel_binding`, então a URL não liga `Include Error Detail` nem manda `options`; `disable`, `allow` e `prefer` só em `Development`. Sem banco nenhum e com `MigrateOnStartup` ligado, a partida para. O erro é um código (`database_url.*`) e a mensagem nunca leva a URL, a senha nem a exceção original.
6. **D6 · Conexão direta e pool de 30.** O Neon de 0,25 CU tem 105 conexões livres; com `maxScale` 1, a revisão velha durante o deploy e o excesso breve do Cloud Run, podem existir 3 processos: 3 × 30 = 90. O valor cobre o mínimo da E5.3a (2 × 8 + 4 = 20). `Connection Idle Lifetime=60` e `Connection Pruning Interval=10` fecham conexões ociosas para não manter o Neon acordado. O pooler do Neon (modo transação) fica de fora por causa da trava de sessão das migrações.
7. **D7 · Migrações na partida** (`Database__MigrateOnStartup=true` no `service.yaml`). Rodam antes de a porta abrir: se falharem, a revisão nova não recebe tráfego e a anterior continua no ar. Toda migração precisa ser compatível com a versão anterior (expandir e depois contrair), porque as duas revisões convivem por alguns segundos. Duas partidas ao mesmo tempo dependem da trava de migração que o EF Core tem desde a versão 9 (no Npgsql, um *advisory lock* de sessão, outro motivo para não usar o pooler); a API usa EF Core 10 com Npgsql 10.0.3. A trava não foi testada com duas partidas reais: fica como risco do roteiro do ambiente.
8. **D8 · `/health` não consulta o banco**: não acorda o Neon e não expõe nada.
9. **D9 · Sem `ForwardedHeaders` agora.** A API não lê IP, esquema nem host da requisição. Quando a E5.3 limitar por IP, o IP confiável no Cloud Run direto é o **último** item de `X-Forwarded-For` (`ForwardLimit=1`), sem doc oficial: a E5.3 testa de verdade (`pendencias.md`). O HTTPS fica com o Cloud Run, sem `UseHttpsRedirection` nem HSTS na API.
10. **D10 · `AllowedHosts` continua `*`**: o front-end do Google já roteia pelo `Host`, e a sonda de partida chama o contêiner com outro `Host`.
11. **D11 · Parada em 8 s** (`HostOptions.ShutdownTimeout`), antes do SIGKILL que vem 10 s depois do SIGTERM.
12. **D12 · Custo zero vigiado:** teto de gasto do Cloud Run no projeto e alerta de orçamento de US$ 1 (resposta 94); limpeza do Artifact Registry com as 5 imagens mais novas; varredura de vulnerabilidade do Artifact Registry desligada (é paga); logs na retenção padrão de 30 dias.
13. **D13 · Volta para um deploy anterior** pelo console ("Gerenciar tráfego") ou por `gcloud run services update-traffic`; o próximo deploy devolve 100% à revisão mais nova (`traffic: latestRevision` no `service.yaml`). Roteiro em [`deploy.md`](../../operacao/deploy.md).

**Alternativas descartadas:** Railway Hobby (US$ 5 por mês); Cloud Build com gatilho do GitHub (precisa do app do Google no repositório e não espera o `ci-ok`); `gcloud run deploy --source` (usa o Cloud Build e não leva o digest testado); chave JSON de conta de serviço (segredo de vida longa no GitHub); `minScale` 1 (sai da faixa grátis); pooler do Neon (trava das migrações); Cloud Run Job para migrar (depois do piloto); `deploy-cloudrun` com flags (sonda pelas flags não confirmada no GA).

## Consequências

- Os dois serviços nascem do script de identidades, públicos e com a imagem de exemplo; o primeiro deploy troca a imagem.
- Dados pessoais e logs de requisição (IP e user agent, 30 dias) ficam nos EUA: Cloud Run em `us-east4`, Neon em `us-east-1` (resposta 91, `dados-pessoais.md`).
- O teto de gasto, se atingido, **pausa a produção** até o mês seguinte ou até o teto subir (DoS financeiro, `modelo-de-ameacas.md`).
- A primeira chamada depois de minutos parado paga a partida do .NET, a conferência das migrações e o Neon acordando. O número sai do caso 22 do plano; acima de 10 s, a resposta 90 volta para o Gabriel.
- `max-instances` pode ser passado por pouco tempo em picos: as cotas da E5.3a valem dobradas nesse instante. Aceito no piloto.
- Sem backup próprio até a E5.3: vale a restauração de 6 h do Neon Free, e a produção só recebe jogadores reais depois da E5.3.
- Um push com vários commits na `main` só olha o último para decidir o deploy; com merge squash isso não acontece. Se acontecer, um commit seguinte que toque a API faz o deploy de tudo.
